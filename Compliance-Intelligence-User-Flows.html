1 End-to-end: Policy document → Resolved compliance violation

The full loop — ingest an SOP, extract & classify rules (including non-observable / needs-clarification), map to physical reality, monitor live, and resolve a fired violation with blocking SOP attestation.

Step notes & rules
  • Gating dependency. Everything downstream assumes a clean rule object. The extracted rule carries: rule text, observable flag, sensor type(s), zone binding, severity, source-doc reference, version, and response-step text. MVP
  • Non-observable is never silent. Rules the system can't watch are tagged honestly and surfaced — not skipped (the “silently ignore” option is explicitly Won't Do). In MVP they're flagged; the automated make-observable routing is flow 4e. Guardrail
  • Degraded ≠ compliant. If a rule's required sensor is offline, monitoring status shows DEGRADED / UNKNOWN, ties to Sensor Health. Guardrail
  • Distinct event type. Compliance events augment/overlay the existing security/safety/ops event rather than creating a duplicate — protects the SOC Operator's “Quiet Cockpit.” MVP
  • Blocking attestation. Resolve Alert stays disabled until every required SOP step is confirmed; each confirmation writes actor + timestamp to Event History. A genuinely un-completable step takes a reason-coded, logged exception path. MVP
  • Conservative launch. One false positive erodes trust faster than ten misses — default sensitivity is low, customers tune up.

Step notes & rules
  • PBAC first. Edit access is gated by the existing Specific Privileges model (extended, not parallel). Compliance/EHS Mgr = CRUD on rules + config; Operator/Responder = read only here. MVP
  • Re-classification on edit. If an edit changes whether a rule is observable, it must re-run the Observable-vs-Not check rather than silently staying active.

  • Delete is special. Destructive with audit implications → restricted to the highest privilege and always logged. Restricted

3 Flagging a false positive from within an event

An operator judges a fired compliance violation to be not a real violation, records why, and (optionally) routes it for admin review — feeding the false-positive metric and future self-improving extraction.

Step notes & rules
  • Reason is mandatory. The operator must say why it isn't a violation — that reason is the trust signal and the training data. MVP
  • Open question surfaced. The requirements flag “may want this escalated to an Admin for review?” — the diagram shows that branch as a policy decision so the team can decide whether dismissal is operator-final or admin-gated.
  • First-class metric. FP rate is a counter-metric that must not get worse; every dismissal is instrumented from day one. MVP
  • Closes the loop later. Confirmed/dismissed events feed the Self-improving Rule Engine. 3.3
